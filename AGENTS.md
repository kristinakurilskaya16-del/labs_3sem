# AGENTS.md — правила работы ИИ-агента

Проект: последовательные лабораторные работы по ООП на C++20. Этот файл действует для всего репозитория `labs_3sem`.

## Активное задание

**Лабораторная №2, только задание со звёздочкой: решающий пень (`DecisionStump`).**

По условию преподавателя звёздочка №2 самодостаточна и заменяет обязательную часть. **Не реализовывать kNN.** Не применять к текущей работе правила обязательной части №2 вместо правил звёздочки.

**Перед каждой задачей агент обязан прочитать `docs/agent_rules/lab_2.md`.** Если файл недоступен, остановиться и запросить его содержимое. Для вопросов об уже выполненной работе №1 использовать `docs/agent_rules/lab_1.md`.

При публикации следующей лабораторной студент обновляет активное задание и файл правил. Не предполагать, что ограничения разных лабораторных совпадают.

## Приоритет и границы помощи

1. Официальное условие текущей лабораторной и её звёздочки определяет допустимое использование ИИ. При сомнениях не генерировать код спорной части; запросить уточнение.
2. Правила активного задания ограничивают общие технические инструкции этого файла.
3. Агент может изучать код и объяснять инструменты, но **не должен генерировать, дописывать, исправлять, рефакторить или проектировать** части, которые студент обязан выполнить самостоятельно. Нельзя обходить запрет переименованием задачи в «оптимизацию», «исправление» или «рефакторинг».
4. До изменений перечислить планируемые файлы и действия и получить согласие студента. Не выполнять `git commit`, `git push`, `git reset`, удаление или перезапись файлов без отдельного разрешения.
5. Сохранять работоспособность предыдущих лабораторных. Если новая работа требует изменить старую реализацию, сначала объяснить необходимость и проверить ограничения обеих работ.
6. Не устанавливать зависимости и не менять настройки окружения без согласия. Ошибки запрещённых частей сообщать студенту без автоматического исправления.
7. Существенную разрешённую помощь фиксировать в журнале соответствующей лабораторной; агент не должен придумывать записи о действиях, которых не было.

## Что разрешено и запрещено в активной работе

**Разрешено с соблюдением условия и журнала:** документирование уже написанного публичного интерфейса ядра (например, Doxygen), настройка и сборка документации; форматирование консольных таблиц; помощь с чтением параметров запуска; вспомогательный код тестов; объяснение сообщений компилятора и санитайзеров; объяснение средств языка и библиотек C++.

**Запрещено:** реализация решающего пня и его алгоритма; реализация индексации матрицы; проектирование иерархии моделей и иерархии исключений. Не генерировать и не исправлять эти части, включая под видом вспомогательного кода. Подробности: `docs/agent_rules/lab_2.md`.

## Структура существующего проекта

- `CMakeLists.txt` — конфигурация сборки.
- `README.md` — описание проекта, датасета, команд и решений.
- `include/{types.hpp,enums.hpp,matrix.hpp,dataset.hpp}` — объявления и типы работы №1.
- `src/{dataset.cpp,matrix.cpp,main.cpp}` — ядро данных, матрица и консольное приложение.
- `tests/tests.cpp` — тесты с `assert`, зарегистрированные в CTest.
- `third_party/cxxopts.hpp` — header-only парсер CLI.
- `data/` — входные и выходные данные; не менять без разрешения.
- `docs/agent_log/lab_1.md` — журнал работы №1.
- `docs/agent_log/lab_2.md` — журнал работы №2 (создать при начале документирования работы).
- `docs/agent_rules/lab_1.md`, `docs/agent_rules/lab_2.md` — ограничения использования ИИ.

Существующая архитектура: библиотека `core` (данные и матрица), приложение `app` (CLI и взаимодействие с пользователем), тестовая цель `tests`. По мере выполнения работ структура может расширяться; сверяться с реальными файлами, не предполагать наличие ещё не созданных классов.

Ключевые типы работы №1: `Column` на основе `std::variant`, пропуски через `std::optional`, стратегии через `enum class`, `DatasetInfo` для статистик, `Matrix` с `Layout::RowMajor`/`ColumnMajor`. Не менять эти решения автоматически.

## Сборка и проверка

- C++20, GCC 12+ или Clang 16+; текущая проверенная среда: WSL с GCC 13.3.0.
- CMake: следовать фактическому `cmake_minimum_required` проекта (по текущей проверке — 3.20+).
- Цели: `core`, `app`, `tests`; предупреждения `-Wall -Wextra`.
- В Debug используются ASan и UBSan; `assert` в тестах должны быть активны (в текущей конфигурации применяется `-UNDEBUG`, а не `NDEBUG=0`).
- Выполнять команды из WSL в `/mnt/c/VSCode/labs_3sem`, использовать отдельный каталог `build-codex`, не трогать существующий `build`:

```bash
cmake -S . -B build-codex -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_COMPILER=g++
cmake --build build-codex --parallel 2
ctest --test-dir build-codex --output-on-failure
```

Если WSL недоступен из песочницы агента, сообщить об ограничении и запросить разрешение пользователя на необходимый запуск. Не считать тесты пройденными без фактического выполнения. Успех санитайзеров относится только к запущенным сценариям.

## Стиль и качество

- Придерживаться существующих соглашений: `PascalCase` для классов и перечислений, `snake_case` для функций и переменных.
- Не добавлять универсальные абстракции или зависимости без требования задания.
- Код ядра не должен печатать ошибки пользователю; для новой работы действуют требования задания №2 об исключениях и их обработке в `main`. **Проектирование иерархии исключений выполняет студент.**
- Документация должна описывать фактический код, а не предполагаемую реализацию. Студент проверяет комментарии перед принятием.

## Журнал использования агента

Для работы №2: `docs/agent_log/lab_2.md`. Записывать значимые запросы, ответы, принятые/отклонённые изменения, проверку и примеры неверных сгенерированных комментариев с исправлениями. Не подменять журнал ошибок программы журналом использования ИИ.

## Задания со звёздочкой в будущем

Студент планирует выполнять звёздочки всех семи работ. **Не переносить разрешения из одной звёздочки в другую.** До получения текста новой звёздочки не писать её код и не утверждать, что генерация разрешена. Правила первой звёздочки строже правил второй: см. `docs/agent_rules/lab_1.md`.
